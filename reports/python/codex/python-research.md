# Python semantic coverage research checklist

## Scope and baseline

This report identifies materially distinct Python behaviors that a broad,
idiomatic, self-contained reference project should exercise. It does not
prescribe a project theme, source layout, graph schema, scoring scheme, or
analysis technique.

- **Baseline language:** Python 3.13 syntax and semantics, with explicit
  compatibility cases for Python 3.8–3.12 and provisional notes for later
  releases.
- **Baseline implementation:** CPython 3.13 on a conventional desktop/server
  operating system.
- **Secondary implementations:** PyPy, GraalPy, Jython, MicroPython, and
  alternate CPython builds are relevant only where implementation behavior
  differs.
- **Packaging baseline:** `pyproject.toml`, a PEP 517 build backend, wheels and
  source distributions, and current PyPA metadata conventions.
- **Typing baseline:** runtime annotations plus the current typing
  specification. Static type checker behavior is not itself language semantics
  and may differ among checkers.
- **Authority labels:** **Language** means the Python language definition;
  **CPython** means official implementation behavior or API; **Packaging** means
  PyPA interoperability standards; **Typing** means the typing specification and
  accepted typing PEPs; **Ecosystem** means a common convention or third-party
  transformation.
- **Evidence interpretation:** “Observable content” describes what must be
  present to expose the behavior, not how files should be organized.
- **Terminology:** Python Enhancement Proposal (**PEP**), Python Packaging
  Authority (**PyPA**), application binary interface (**ABI**), abstract syntax
  tree (**AST**), just-in-time compilation (**JIT**), version control system
  (**VCS**), and object-relational mapper (**ORM**) are abbreviated below.

## Implementation-defined, unspecified, or intentionally unstable behavior

- Object destruction and weak-reference callback timing are not portable. CPython
  reference counting often makes them appear deterministic.
- Thread interleaving and accidental atomicity of built-in operations are not a
  synchronization contract. Free-threaded builds expose more schedules.
- Hash values, set iteration order, object addresses, interning, allocator
  behavior, and many representation details can change by run or implementation.
- Structural pattern matching intentionally leaves some partial-binding state
  and protocol call counts unspecified.
- Exact exception and warning messages, suggestions, source spans, traceback
  rendering, and compiler warnings change between CPython releases.
- Bytecode, opcode specialization, frame internals, code-object fields, abstract
  syntax tree details, marshal format, and cache files are CPython/version
  details.
- Native extension layout, stable/application binary interface support, symbol
  naming, calling conventions, and subinterpreter/free-threaded safety are build
  and platform dependent.
- Float edge cases depend partly on platform C library and hardware. Integer
  semantics are language-defined, but conversion to fixed-width native types is
  not arbitrary precision.
- Import order is specified at a useful semantic level, but search roots and
  available artifacts depend on invocation, environment, installer, filesystem,
  and hooks.
- Static typing is not runtime enforcement. Checker diagnostics, inference,
  plugin behavior, and acceptance of incompletely specified edge cases can
  differ.
- Framework-generated members, route/model registries, dependency injection,
  and plugin discovery are ecosystem contracts whose meaning depends on library
  version and configuration.

## Known knowledge gaps and verification priorities

- Python 3.14-and-later details are provisional. The exact default annotation
  semantics, new syntax, finalized subinterpreter API, multiprocessing defaults,
  and removed deprecated APIs need release-document verification.
- Free-threaded CPython support is moving quickly. Extension compatibility
  declarations, wheel tags, implicit lock enabling, and standard-library
  guarantees need build-specific verification.
- PEP 751 lock-file adoption and the exact relationship to existing tool formats
  need current packaging-spec verification.
- New typing features after 3.13, especially closed typed dictionaries, extra
  items, `TypeIs`, annotation evaluation APIs, and defaults on all type-parameter
  forms, need checker-independent specification verification.
- Alternate implementations are underrepresented. PyPy’s extension emulation,
  GraalPy native compatibility, Jython’s supported Python level, and MicroPython
  grammar/library subsets need their own official documentation.
- Native binding ecosystems are deliberately grouped. Cython, CFFI, pybind11,
  nanobind, and Rust/PyO3 each add distinct generated entities and ownership rules
  that may justify separate items in a dependency-specific expansion.
- Framework conventions are representative, not exhaustive. Django, SQLAlchemy,
  Pydantic, attrs, FastAPI, Flask, Click/Typer, pytest, and plugin systems differ
  materially and should be verified only if selected dependencies bring them
  into scope.
- Packaging backend differences are grouped. Setuptools, Hatchling, Flit,
  Poetry-core, Meson-Python, scikit-build-core, and Maturin have distinct
  discovery and generated/native build behavior.

## Final audit for potentially missing feature families

| Family audited | Coverage status | Residual risk |
|---|---|---|
| Parsing, binding, scopes, imports, and execution | Broadly covered | Interactive parser recovery and highly dynamic import hooks can add more implementation-specific cases. |
| Functions, decorators, generators, coroutines, and dispatch | Broadly covered | Third-party multimethod and aspect/proxy systems are only represented by the general registry/decorator cases. |
| Classes, metaclasses, descriptors, inheritance, and generated models | Broadly covered | Individual ORMs/model libraries can synthesize much larger hidden APIs. |
| Data protocols, operators, context managers, serialization, and lifetime | Broadly covered | Decimal/fraction/array interoperability and buffer-export edge cases could merit dependency-specific expansion. |
| Exceptions, warnings, control transfer, and structural patterns | Broadly covered | Exact diagnostic recovery and implementation call traces remain intentionally unstable. |
| Typing, stubs, generics, narrowing, and deferred annotations | Broadly covered through 3.13 | 3.14+ annotation and typing changes are the largest language-level verification gap. |
| Async, threads, processes, contexts, signals, and subinterpreters | Broadly covered | Distributed task systems and green-thread/event-loop replacements are ecosystem-specific omissions. |
| Build, packaging, artifacts, dependencies, resources, and native code | Broadly covered | Backend-specific editable/native behavior and the newest lock standard need current verification. |
| Tests, notebooks, logging, command lines, plugins, and frameworks | Representative coverage | Coverage is intentionally by semantic mechanism, not by enumerating libraries. |
| Platforms and implementations | Core differences covered | Embedded, browser/WebAssembly, mobile, and JVM/.NET-hosted Python variants remain thin. |
| Invalid and ambiguous programs | Broad failure-phase coverage | Security policy, sandbox, import integrity, and hostile package cases are outside ordinary language semantics and only indirectly covered. |

No obvious core Python feature family is wholly absent. The highest-risk
omissions are release-specific behavior after Python 3.13, alternate
implementations, and dependency-specific code generation or metaprogramming.
