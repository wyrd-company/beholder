# Comprehensive Python Feature Coverage for a Code-Graph Reference Project

**Key Points**
* The accurate generation and validation of a Python code-graph necessitates a profound, nuanced handling of both the language's static Abstract Syntax Tree (AST) features and its extensive runtime dynamism. 
* Recent Python semantic evolutions, notably the introduction of PEP 695 generics and PEP 634 structural pattern matching, introduce entirely new classes of semantic entities, type variables, and scope bindings that must be natively modeled by graph generators.
* Build systems and ecosystem conventions—such as `pyproject.toml` standardizations, `py.typed` markers, and the architectural divergence between `src/` and flat repository layouts—fundamentally alter module resolution algorithms and visibility boundaries.
* A critical tension exists between static analysis visibility (e.g., imports guarded by `TYPE_CHECKING` blocks) and runtime execution. This poses a significant challenge for graph generators attempting to faithfully represent the developer's intent across disparate environments.
* Research suggests that an idiomatic, self-contained reference project cannot merely test individual grammar productions in a vacuum; it must rigorously exercise the complex, often unpredictable interactions between packaging metadata, dynamic language features, and toolchain constraints.

**Overview of Code-Graph Requirements**
A code graph is a specialized data structure that models the semantic entities of a codebase (such as classes, functions, modules, and variables) as nodes, and their relationships (such as inheritance, instantiation, function calls, and import bindings) as edges. To be considered accurate and complete, a code-graph generator must correctly parse source code, resolve identical entities across multiple files, and deduce the types and scopes of variables. In a highly dynamic language like Python, where types are often implicit and module resolution depends heavily on the runtime configuration of `sys.path` and the specific execution environment, generating a static code graph is notoriously difficult. The reference project outlined in this report is designed to stress-test these generators. It acts as an authoritative benchmark, containing specific project topologies and code idioms that deliberately expose the edge cases of Python's execution model. The code graph must transcend basic lexical analysis to represent the true semantic meaning of the program as it would be interpreted by the official Python runtime and modern language servers.

**Scope of the Research**
This academic research report compiles an exhaustive, source-grounded checklist of Python language, toolchain, build, package, and common ecosystem features. The investigation is explicitly scoped to identify those behaviors that, if omitted from a reference fixture, would leave a material gap in the evaluation of a code-graph generator. The scope encompasses language-defined semantics, official compiler and interpreter behaviors, module resolution boundaries, package management via modern standards (e.g., PEP 517, PEP 621), generated program elements, and the profound impacts of ecosystem conventions like static typing distribution. The report rigorously avoids cataloging every standard-library function or elementary grammar production. Instead, it prioritizes systemic distinctions that require meaningfully different project content, semantic interpretation, build treatment, or diagnostic behavior.

## 1. Introduction and Methodological Framework

The Python programming language has undergone a radical transformation over the last decade. Originally conceived as a dynamically typed scripting language, it has evolved into a robust ecosystem capable of supporting massive, enterprise-scale applications. This evolution has been driven by the introduction of gradual typing (PEP 484), standardized packaging metadata (PEP 517, PEP 621), and complex syntactical additions like structural pattern matching (PEP 634). For researchers and engineers developing static analysis tools, language servers, and code-graph generators, this rapid evolution presents a moving target. 

A code-graph generator must map the physical text of a repository into a strict, queried semantic model. When a Python script executes `from package import module`, the resolution of that edge depends on a staggering number of variables: the presence of `__init__.py` files, the layout of the repository (`src/` vs. flat), the content of `sys.path`, the existence of `.pth` files from editable installs, and the potential runtime manipulations of `importlib`. Furthermore, the internal semantic structure of the module is dictated by dynamic constructs such as metaclasses, descriptor protocols, and AST-synthesized methods generated by decorators like `@dataclass`.

The central research objective of this report is to compile a comprehensive, source-grounded checklist of these behaviors. The central research question asks: *Which materially distinct Python behaviors and project conditions must be represented so that omitting one would leave a meaningful gap in the coverage of a code-graph reference project?*

To answer this, the research strategy prioritized official Python Enhancement Proposals (PEPs), the Python Language Reference, and maintainer-owned documentation for foundational build tools (e.g., setuptools, pip). The ensuing checklist is categorized into five major domains:
1. Module Systems, Packages, and Workspaces
2. Build Systems and Package Environments
3. Dynamic Execution and Resolution
4. Language-Defined Semantics and Constructs
5. Type Hinting, Static Analysis, and Ecosystem Conventions

## 2. Source-Grounded Checklist of Python Features

### 2.1. Module System, Packages, and Workspaces

#### 2.1.1. Implicit Namespace Packages (PEP 420)

* **Report-local stable identifier:** `PY-MOD-001`
* **Feature or behavior name:** Implicit Namespace Packages (PEP 420)
* **Description of the materially distinct behavior:** 
  Prior to Python 3.3, the Python import system strictly required the presence of an `__init__.py` file within a directory for that directory to be recognized and imported as a package. Directories lacking this file were ignored during the module search process. PEP 420 radically altered this semantic behavior by introducing "implicit namespace packages" [cite: 1, 2]. During import processing, when the import machinery searches for a package named `foo`, it iterates over each directory in the parent path. If `<directory>/foo/__init__.py` is found, a regular package is returned. However, if no `__init__.py` is found, the import machinery does not immediately fail; instead, it continues to search all directories on `sys.path`. It constructs a virtual namespace package that acts as a mechanism for splitting a single Python package across multiple distinct directories on disk [cite: 1, 3]. The import machinery automatically computes and manages the `__path__` attribute for this namespace. For a code-graph generator, this represents a massive paradigm shift. A traditional graph generator might assume a one-to-one mapping between a package node and a physical directory containing an `__init__.py` file. With PEP 420, the "node" representing the package `foo` is completely virtual and composite. The graph must represent a unified semantic entity that aggregates portions from disparate physical locations across the workspace [cite: 1, 3].
* **Observable project content that would demonstrate it:** 
  A reference project should include a workspace with multiple independent library directories added to the Python path. For example, `lib_a/company/utils/strings.py` and `lib_b/company/utils/math.py`. Neither the `company` nor the `utils` directories should contain an `__init__.py` file. A consumer script at the root level would execute `from company.utils import strings, math`. The graph generator must successfully resolve both imports to their respective, physically separated source files, unifying them under the `company.utils` namespace node.
* **Important variants, interactions, counterexamples, and failure cases:** 
  A critical failure case occurs when implicit namespace packages collide with regular packages. If a directory containing `company/utils/__init__.py` is placed earlier in the `sys.path`, the import machinery will halt and return the regular package, completely ignoring the namespace portions found later in the path [cite: 1, 2]. Code-graph generators often fail to correctly implement this precedence, either merging the regular package with the namespace package or failing to resolve the namespace portions entirely. Furthermore, the dynamic nature of the `__path__` attribute (specifically the `_NamespacePath` object) can confuse static analyzers that expect a static string or list of strings [cite: 3, 4].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Requires Python 3.3 or higher. The behavior is deeply integrated into the native `importlib` machinery and requires no external packages.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 1, 2], [cite: 3, 4].
* **Confidence:** 
  High.

#### 2.1.2. Legacy Namespace Packages (`pkgutil` and `setuptools`)

* **Report-local stable identifier:** `PY-MOD-002`
* **Feature or behavior name:** Legacy Namespace Packages (`pkgutil` and `setuptools`)
* **Description of the materially distinct behavior:** 
  Before the formal standardization of implicit namespace packages in PEP 420, the Python ecosystem relied on runtime hacks to achieve the distribution of a single package across multiple directories. These techniques are still heavily prevalent in legacy codebases and older scientific packages. The two primary methods involve creating an explicit `__init__.py` file in the namespace directory and mutating the `__path__` variable at runtime. The `pkgutil` method uses the standard library: `__path__ = __import__('pkgutil').extend_path(__path__, __name__)` [cite: 5]. The `setuptools` method uses a similar injection: `__import__('pkg_resources').declare_namespace(__name__)` [cite: 5]. Alternatively, `setuptools` relies on injecting `.pth` files into the environment during installation, which automatically inject the namespace into Python without requiring explicit code in the `__init__.py` [cite: 5]. A correct code graph must recognize these specific syntactical idioms not as regular code execution, but as topological directives that merge directories. If a graph generator treats an `__init__.py` containing `declare_namespace` as a standard, isolated package initialization, it will fail to link dependencies that exist in other directory portions of the same namespace.
* **Observable project content that would demonstrate it:** 
  A project fixture containing two directories: `legacy_lib_1/zope/interface/` and `legacy_lib_2/zope/event/`. The `zope` directories in both paths must contain an `__init__.py` file executing the `pkgutil.extend_path` boilerplate. The evaluation test will verify that a script importing `zope.interface` and `zope.event` correctly resolves edges to both physical directories, treating the `zope` node as a shared namespace despite the presence of `__init__.py` files.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The most complex interaction occurs when legacy namespace packages are mixed with PEP 420 namespace packages. Because PEP 420 specifies that the presence of an `__init__.py` file halts the namespace search and denotes a regular package, placing a `pkgutil`-style `__init__.py` in one portion of a namespace will effectively break the PEP 420 portions of that namespace that do not have the `__init__.py` file, depending heavily on the order of resolution in `sys.path` [cite: 1, 5].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Supported on all Python versions, though officially discouraged in favor of PEP 420 for Python 3.3+. Requires `setuptools` for the `pkg_resources` variant.
* **Classification:** 
  Ecosystem convention and toolchain behavior.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 1, 5].
* **Confidence:** 
  High.

#### 2.1.3. Source Layout (`src/`) vs. Flat Layout Import Path Semantics

* **Report-local stable identifier:** `PY-MOD-003`
* **Feature or behavior name:** Source Layout vs. Flat Layout Import Path Semantics
* **Description of the materially distinct behavior:** 
  The structural arrangement of files in a Python repository fundamentally alters how the Python interpreter and testing frameworks resolve module imports. The "flat layout" places the package source code directly at the root of the project repository (e.g., `project_root/my_package/`). Because the Python interpreter automatically prepends the current working directory (`.`) to the beginning of `sys.path`, running a script or test from the project root will cause `import my_package` to resolve directly to the local directory, completely bypassing the installed package environment [cite: 6, 7]. Conversely, the "src layout" nests the package code inside a generic subdirectory (e.g., `project_root/src/my_package/`). Because `src/` is not added to `sys.path` by default, attempting to `import my_package` from the project root will result in a `ModuleNotFoundError` unless the package has been formally installed (typically via an editable install) into the virtual environment [cite: 6, 8]. For a code-graph generator, this layout distinction changes the entire topological mapping of the project. A generator must accurately simulate the `sys.path` behavior of the target environment to build valid edges [cite: 7, 9]. If a generator assumes all top-level directories are importable, it will hallucinate import edges in a `src/` layout that would fail at runtime.
* **Observable project content that would demonstrate it:** 
  Two parallel fixture projects. Fixture A uses a flat layout with `project_a/awesome_package/module.py` and `project_a/tests/test_module.py`. Fixture B uses a src layout with `project_b/src/awesome_package/module.py` and `project_b/tests/test_module.py`. The graph generator must be evaluated on its ability to correctly identify `awesome_package` as the root importable entity in both scenarios, while recognizing that in Fixture B, the `src` directory itself is not a valid Python module or namespace.
* **Important variants, interactions, counterexamples, and failure cases:** 
  A common failure case with flat layouts is "import hell" or shadowing, where a development copy of a package accidentally shadows a globally installed package of the same name due to the current working directory taking precedence in `sys.path` [cite: 7, 8]. Another variant is when developers incorrectly add `__init__.py` to the `src/` directory, accidentally turning `src` into a package and requiring imports like `from src.awesome_package import module`, which completely defeats the packaging purpose and ruins the code graph [cite: 8, 9].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Applicable across all modern Python versions. Strongly associated with packaging toolchains like `setuptools`, `hatch`, and `uv`.
* **Classification:** 
  Ecosystem convention and normative interpreter behavior (`sys.path` initialization).
* **Direct citations to the primary sources supporting the item:** 
  [cite: 6, 7], [cite: 8, 9].
* **Confidence:** 
  High.

#### 2.1.4. Explicit Export Visibility (`__all__`)

* **Report-local stable identifier:** `PY-MOD-004`
* **Feature or behavior name:** Explicit Export Visibility via `__all__`
* **Description of the materially distinct behavior:** 
  In Python, the concept of "public" versus "private" module attributes is historically governed by naming conventions (e.g., prefixing a variable with an underscore). However, the language provides a concrete semantic mechanism for defining a module's public export API: the `__all__` list [cite: 10, 11]. When a consumer module executes a wildcard import (e.g., `from spam import *`), the Python interpreter inspects the `spam` module for the presence of the `__all__` attribute. If it exists, it must be a sequence of strings, and the interpreter will strictly bind only the names specified in that sequence into the consuming module's namespace [cite: 10, 12]. If `__all__` is absent, the interpreter falls back to importing all names that do not begin with an underscore. For a code-graph generator, `__all__` serves as a rigid visibility boundary. The graph must intercept wildcard import statements and conditionally generate edges based on the evaluation of the `__all__` variable [cite: 12, 13]. Failure to evaluate `__all__` will result in massive graph pollution, as internal imports, helper functions, and private constants from the target module will be incorrectly linked into the consumer's namespace.
* **Observable project content that would demonstrate it:** 
  A module `api.py` containing `__all__ = ['public_func', 'PublicClass']`, alongside definitions for `public_func`, `PublicClass`, `internal_func`, and an imported module `sys`. A consumer script `main.py` containing `from api import *`. The generated code graph must contain edges from `main.py` to `public_func` and `PublicClass`, but explicitly *must not* contain edges to `internal_func` or `sys`.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The most difficult variant for static analysis occurs when `__all__` is mutated dynamically at runtime, for instance via `__all__.append('extra_func')` or `__all__ = [name for name in dir() if not name.startswith('_')]`. While PEP 842 proposed a new `__export__` mechanism to clean this up, it was rejected, cementing `__all__` as the standard [cite: 13]. If a code graph cannot partially evaluate AST lists, it will fail to resolve the exports. Note that `__all__` only governs wildcard imports; a consumer can still explicitly bypass it via `from api import internal_func`, which the graph must accurately represent as a valid edge [cite: 10, 14].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Standard Python language feature, valid in all versions.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 10, 11], [cite: 12, 13].
* **Confidence:** 
  High.

### 2.2. Build Systems and Package Environments

#### 2.2.1. Standardized Project Metadata (`pyproject.toml` / PEP 517 & 621)

* **Report-local stable identifier:** `PY-BLD-001`
* **Feature or behavior name:** Declarative Project Metadata (`pyproject.toml`)
* **Description of the materially distinct behavior:** 
  Before PEP 517, the Python packaging ecosystem was heavily coupled to the executable `setup.py` script provided by `setuptools`. This meant that determining project metadata, dependencies, and build requirements required executing arbitrary, untrusted Python code. PEP 517 introduced a standardized interface for build backends, decoupling the frontend installer (like `pip`) from the backend (like `setuptools`, `flit`, or `hatchling`) [cite: 15, 16]. Subsequently, PEP 621 standardized the `[project]` table within the `pyproject.toml` configuration file, allowing developers to declare core metadata (name, version, dependencies, entry points) statically [cite: 17, 18]. For a code-graph generator, `pyproject.toml` is the definitive source of truth for the project's identity, its external dependency graph, and its visibility boundaries. The generator must parse this TOML file to understand the package name, the entry points (which act as roots for the call graph), and the build-system requirements [cite: 15, 19]. If a generator ignores `pyproject.toml` in favor of legacy `setup.py` scanning, it will fail to analyze modern, compliant Python packages correctly.
* **Observable project content that would demonstrate it:** 
  A project utilizing a modern build backend like `hatchling`, containing only a `pyproject.toml` file with `[build-system]` and `[project]` tables, and completely lacking a `setup.py` or `setup.cfg` file. The `pyproject.toml` will declare project dependencies and a CLI script entry point under `[project.scripts]`. The code graph must extract these dependencies and map the CLI script name to the corresponding function in the source code.
* **Important variants, interactions, counterexamples, and failure cases:** 
  A complex interaction occurs when tools like Poetry use their own legacy `[tool.poetry]` tables instead of the standardized `[project]` table [cite: 16, 19]. A resilient code graph must be capable of understanding both PEP 621 standards and widespread proprietary fallbacks. Furthermore, some projects use the `dynamic` key in PEP 621 to indicate that fields like `version` or `dependencies` are computed dynamically by the build backend, effectively blinding static analysis tools [cite: 17, 18].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Applies to modern packaging toolchains (`pip >= 19.0`, `setuptools >= 61.0`).
* **Classification:** 
  Normative toolchain standard (Python Packaging Authority / PyPA).
* **Direct citations to the primary sources supporting the item:** 
  [cite: 15, 17], [cite: 16, 19].
* **Confidence:** 
  High.

#### 2.2.2. Editable Installations and Import Hooks (PEP 660)

* **Report-local stable identifier:** `PY-BLD-002`
* **Feature or behavior name:** Editable Installations (PEP 660)
* **Description of the materially distinct behavior:** 
  An "editable install" (historically invoked via `pip install -e .` or `python setup.py develop`) allows a developer to install a Python package into a virtual environment in such a way that changes to the source code are immediately reflected without requiring a reinstallation [cite: 20, 21]. Before PEP 660, this was an exclusive, hardcoded feature of `setuptools`. PEP 660 standardized this by adding specific hooks (`build_editable`) to the PEP 517 build backend interface [cite: 21, 22]. Under the hood, modern backends implement this by generating a `.pth` file inside the environment's `site-packages` directory. This `.pth` file can contain static directory paths, or, in more complex scenarios (especially with flat layouts), it can contain executable Python code that registers custom import finders and hooks into `sys.meta_path` to intercept imports and redirect them to the source tree [cite: 22, 23]. For a code-graph generator attempting to analyze an installed workspace, these import hooks pose an extreme challenge. The graph cannot simply look at physical directories in `site-packages`; it must either statically emulate the complex logic of the custom PEP 660 finders or execute the `.pth` files in a sandboxed environment to discover the true location of the source code [cite: 20, 24].
* **Observable project content that would demonstrate it:** 
  A workspace containing a virtual environment where a package `my_complex_pkg` has been installed in editable mode using `setuptools` with a flat layout. The `site-packages` directory will contain an `__editable__.my_complex_pkg.pth` file containing dynamic import hook code, rather than a simple string path. The graph must successfully resolve an absolute import of `my_complex_pkg` from an external script to the local development source tree.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The implementation of PEP 660 is entirely backend-dependent. `hatchling` might use static `.pth` paths, while `setuptools` defaults to strict mode utilizing dynamic link farms or `sys.meta_path` finders to prevent exposing auxiliary repository files to the interpreter [cite: 23, 24]. Code-graph generators often fail with "Unresolved reference" errors (as seen in IDEs like PyCharm) because they cannot index the dynamic `.pth` dependencies [cite: 24].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Requires PEP 660 compliant build backends and installers (e.g., `pip >= 21.3`).
* **Classification:** 
  Normative toolchain standard.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 20, 22], [cite: 21, 23].
* **Confidence:** 
  High.

### 2.3. Dynamic Execution and Resolution

#### 2.3.1. Dynamic Module Import via `importlib`

* **Report-local stable identifier:** `PY-DYN-001`
* **Feature or behavior name:** Dynamic Module Import via `importlib`
* **Description of the materially distinct behavior:** 
  While standard imports in Python are lexically declared using the `import` and `from ... import` keywords, the language provides the `importlib` package to programmatically interact with the import system at runtime [cite: 25, 26]. Functions such as `importlib.import_module(name)` allow developers to load modules where the `name` is a dynamically constructed string (e.g., determined by a configuration file, user input, or a plugin system) [cite: 27, 28]. Furthermore, lower-level constructs like `importlib.util.spec_from_file_location` and `module_from_spec` allow arbitrary files on disk to be executed and loaded as modules, bypassing the standard `sys.path` entirely [cite: 26, 29]. For a code-graph generator, dynamic imports represent a fundamental discontinuity in static analysis. Because the module name is not known until runtime, a purely static AST parser cannot determine which module is being imported, resulting in missing edges [cite: 30, 31]. Advanced graph generators must employ techniques such as constant propagation, string interpolation tracking, or partial evaluation to infer the targets of `import_module` calls.
* **Observable project content that would demonstrate it:** 
  A plugin architecture where a core module reads a configuration dictionary, iterates over a list of string names (e.g., `["plugins.auth", "plugins.logging"]`), and calls `importlib.import_module(plugin_name)` in a loop [cite: 31, 32]. The returned module objects are then used to instantiate classes via `getattr(module, 'PluginClass')()`. The code graph should attempt to resolve these edges, or at minimum, flag the dynamic binding sites.
* **Important variants, interactions, counterexamples, and failure cases:** 
  A major complexity arises with the global `sys.modules` dictionary. If a dynamic import fails, or if a developer manually manipulates `sys.modules` to map a string name to an entirely different module object (a technique sometimes used for mocking or hot-reloading), the runtime identity of the module completely diverges from its physical source path [cite: 25, 28]. The usage of the legacy, deeply discouraged `__import__` built-in function presents another syntactical variant that graph generators must support [cite: 30, 31].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Core language feature, supported in all modern Python versions (specifically `importlib` API from Python 3.1+).
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 27, 28], [cite: 25, 26].
* **Confidence:** 
  High.

#### 2.3.2. Metaclasses and the Method Resolution Order (MRO)

* **Report-local stable identifier:** `PY-DYN-002`
* **Feature or behavior name:** Metaclasses and Method Resolution Order (MRO)
* **Description of the materially distinct behavior:** 
  Python's object-oriented architecture is profoundly dynamic. When a class inherits from multiple parent classes, the Python interpreter must determine the exact sequence in which to search for methods and attributes. This is governed by the Method Resolution Order (MRO), which utilizes the C3 linearization algorithm [cite: 33, 34]. The MRO guarantees that a class always appears before its parents, and preserves the order of multiple base classes. Furthermore, classes themselves are objects, meaning they are instances of a higher-level object known as a metaclass (by default, `type`) [cite: 33, 35]. Metaclasses allow developers to intercept the creation of a class object, modify its `__dict__`, dynamically inject or alter methods, and even change the resulting MRO [cite: 34, 36]. For a code graph, resolving a method call like `obj.action()` is highly non-trivial. The generator must algorithmically emulate the C3 linearization to trace the inheritance graph and find the correct definition of `action()` across multiple parent classes [cite: 33, 34]. If a metaclass dynamically alters the class namespace during instantiation, the static AST will completely diverge from the runtime object model, forcing the graph to model synthesized properties.
* **Observable project content that would demonstrate it:** 
  A diamond inheritance structure: Class `D` inherits from `B` and `C`, both of which inherit from `A`. All four classes define a method `process()`. A call to `super().process()` inside `B` will dispatch to `C` (not `A`), due to the cooperative multiple inheritance facilitated by the C3 MRO. The graph must trace this dispatch edge from `B` to `C`. Additionally, a metaclass `SingletonMeta` that overrides `__new__` and manipulates the class attributes upon creation.
* **Important variants, interactions, counterexamples, and failure cases:** 
  Failure to calculate the C3 MRO statically is a common flaw in elementary code-graph generators, resulting in edges pointing to the wrong method implementation in deep hierarchies. Metaclasses that dynamically rename attributes (e.g., ORM models in Django or SQLAlchemy) are almost impossible to resolve purely via AST, requiring hardcoded plugins or runtime tracing to map the generated identities correctly [cite: 34, 37].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Core language feature (New-style classes since Python 2.2, standard in Python 3).
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 33, 34].
* **Confidence:** 
  High.

#### 2.3.3. The Descriptor Protocol

* **Report-local stable identifier:** `PY-DYN-003`
* **Feature or behavior name:** The Descriptor Protocol (`__get__`, `__set__`, `__delete__`)
* **Description of the materially distinct behavior:** 
  In Python, attribute access is not simply a dictionary lookup in memory. When a developer executes `obj.x`, the interpreter delegates the lookup to the `__getattribute__` machinery. If the attribute `x` is found on the class (or its base classes) and it happens to be an object that implements any of the methods `__get__`, `__set__`, or `__delete__`, Python intercepts the default dictionary lookup and invokes the descriptor method instead [cite: 33, 37]. Descriptors are the foundational mechanism underlying Python's properties (`@property`), class methods (`@classmethod`), and static methods (`@staticmethod`) [cite: 36, 38]. They are categorized into "data descriptors" (defining `__set__` or `__delete__`) and "non-data descriptors" (defining only `__get__`), which carry different precedences in the lookup chain [cite: 38]. For a code graph, this means that a seemingly benign variable access (`x = obj.value`) is semantically identical to a function call [cite: 34, 37]. The generator must recognize descriptors and map the attribute read/write operations as directed edge calls to the respective `__get__` or `__set__` methods of the descriptor object.
* **Observable project content that would demonstrate it:** 
  A custom descriptor class `ValidatedField` implementing `__get__` and `__set__`. A host class `Person` instantiating `age = ValidatedField()`. The test code executes `p = Person(); p.age = 30; print(p.age)`. The code graph must trace the assignment `p.age = 30` as a call edge to `ValidatedField.__set__`, rather than a simple assignment to an instance variable.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The distinction between data and non-data descriptors is paramount. If an instance dictionary contains a key `x`, and the class contains a non-data descriptor `x`, the instance dictionary takes precedence. However, if the class contains a data descriptor `x`, the descriptor takes precedence over the instance dictionary [cite: 33, 38]. Static analysis tools frequently fail to model this precedence, resulting in incorrect type inference and missing call edges. Additionally, the optional `__set_name__` method, called during class creation, binds the descriptor to its variable name dynamically [cite: 36, 37].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Core language feature.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 33, 37], [cite: 34, 38].
* **Confidence:** 
  High.

### 2.4. Language-Defined Semantics and Constructs

#### 2.4.1. Class-Private Variable Name Mangling

* **Report-local stable identifier:** `PY-LAN-001`
* **Feature or behavior name:** Class-Private Variable Name Mangling
* **Description of the materially distinct behavior:** 
  Python does not possess strictly enforced access modifiers (like `private` or `protected` in Java or C++). Instead, it relies on conventions. A single leading underscore (e.g., `_internal`) signals that an attribute is meant for internal use, though it is not syntactically enforced [cite: 39, 40]. However, a double leading underscore (e.g., `__hidden`) triggers a normative syntactical mechanism known as "name mangling." When the Python compiler encounters an attribute or method starting with at least two underscores and at most one trailing underscore, it automatically rewrites the name to include the class name, effectively changing it to `_ClassName__hidden` [cite: 39, 41]. This is specifically designed to prevent accidental name collisions when a class is subclassed [cite: 40, 42]. For a code-graph generator, name mangling alters the fundamental identity of the semantic entity at compile time. The graph must link the lexical token `__hidden` used inside the class methods to the mangled identity `_ClassName__hidden` [cite: 39, 41]. If external code intentionally bypasses the privacy by explicitly calling `obj._ClassName__hidden`, the graph must successfully resolve this edge back to the original `__hidden` declaration.
* **Observable project content that would demonstrate it:** 
  A base class `Account` with a mangled attribute `self.__balance`. A subclass `SavingsAccount` that also declares `self.__balance`. The graph must represent these as two entirely distinct nodes in the semantic model (`_Account__balance` and `_SavingsAccount__balance`), and verify that methods within `SavingsAccount` bind to its own mangled variable, preventing cross-pollution.
* **Important variants, interactions, counterexamples, and failure cases:** 
  A notable edge case is that identifiers starting and ending with double underscores (magic/dunder methods like `__init__`) are immune to name mangling [cite: 39, 41]. Additionally, if the class name itself consists only of underscores, mangling behavior can become highly obscure. A graph generator failing to apply mangling will incorrectly collapse variables from subclasses into the parent class, creating false dependency edges and violating the semantic intent of the privacy abstraction [cite: 41, 42].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Core language feature.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:**

#### 2.4.2. Structural Pattern Matching (PEP 634)

* **Report-local stable identifier:** `PY-LAN-002`
* **Feature or behavior name:** Structural Pattern Matching (PEP 634)
* **Description of the materially distinct behavior:** 
  Introduced in Python 3.10, PEP 634 added structural pattern matching via the `match` and `case` statements. This is far more profound than a standard `switch/case` control flow mechanism found in C-like languages [cite: 43, 44]. It combines type matching, data destructuring, and variable binding into a single, cohesive syntax. The `match` statement evaluates a subject expression and attempts to fit it against multiple patterns [cite: 45, 46]. Crucially, when a pattern succeeds (e.g., matching a list `[x, y]` or a class `Point(x=x_val, y=y_val)`), it actively unpacks the subject and binds the nested values to the new local variables (`x`, `y`, `x_val`, `y_val`) [cite: 43, 44]. For a code-graph generator, this represents the creation of entirely new semantic entities and scope bindings. The generator must trace the flow of data from the subject expression, through the pattern destructuring, to the newly bound local variables. Furthermore, the names bound during a successful pattern match leak out and outlive the `case` block, remaining accessible in the enclosing function scope [cite: 45, 46]. The graph must map these variables correctly to prevent unresolved reference errors downstream.
* **Observable project content that would demonstrate it:** 
  A function parsing an API response that uses a complex `match` statement. Cases should include an OR pattern (`case int(val) | float(val):`), a sequence pattern (`case [first, second, *rest]:`), and an AS pattern (`case {"error": code} as err_dict:`). The graph must identify `val`, `first`, `second`, `rest`, `code`, and `err_dict` as formally declared local variables, carrying the correct inferred types derived from the structure of the subject.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The single underscore `_` acts as a wildcard and, unlike other variables, does *not* bind to a value [cite: 45, 46]. Additionally, in an OR pattern (`|`), every subpattern must bind exactly the same set of names; failure to do so is a syntax error [cite: 43, 45]. Dotted names (e.g., `case Constants.VALUE:`) act as literal value comparisons rather than variable bindings [cite: 44, 46]. Code-graph generators built on older parsers often treat `match` and `case` as standard function calls or fail to recognize the scoping leakage, resulting in severed data-flow edges.
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Strictly requires Python 3.10 or higher.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 43, 44], [cite: 45, 46].
* **Confidence:** 
  High.

#### 2.4.3. AST Synthesized Methods (`@dataclass` and `NamedTuple`)

* **Report-local stable identifier:** `PY-LAN-003`
* **Feature or behavior name:** AST Synthesized Methods (`@dataclass` and `NamedTuple`)
* **Description of the materially distinct behavior:** 
  Writing class boilerplate in Python—such as `__init__`, `__repr__`, and `__eq__` methods—can be highly repetitive. Python addresses this through dynamic code generators. The `@dataclass` decorator (introduced in Python 3.7 via PEP 557) scans a class definition for variables with type annotations and dynamically synthesizes these foundational methods at runtime [cite: 47, 48]. Similarly, `typing.NamedTuple` and `collections.namedtuple` generate immutable classes backed by C-level tuples, automatically providing property getters and instantiation logic [cite: 49, 50]. For a code-graph generator, these decorators pose a severe visibility problem. Because the `__init__` method of a dataclass is generated at runtime, it does not physically exist in the source code AST [cite: 47, 48]. When external code instantiates the dataclass (e.g., `Point(x=10, y=20)`), a naive static parser will flag this as an invalid call or fail to resolve the parameter names to the class fields. To produce an accurate code graph, the generator must include specialized logic to intercept these decorators, statically emulate their runtime code generation, and synthesize virtual AST nodes for the methods and properties they create [cite: 47, 51].
* **Observable project content that would demonstrate it:** 
  A `@dataclass` named `InventoryItem` defining type-annotated fields for `name: str`, `unit_price: float`, and `quantity_on_hand: int = 0`. An external script instantiates the class using kwargs. The code graph must explicitly contain a virtual node for `InventoryItem.__init__` with the exact signature derived from the fields, and route the instantiation call edge to this synthesized node. Additionally, the graph must account for `__post_init__` if present [cite: 48, 50].
* **Important variants, interactions, counterexamples, and failure cases:** 
  Dataclasses support inheritance. If a dataclass inherits from another dataclass, the fields are merged, and the synthesized `__init__` signature must reflect the combined fields in a specific order (base fields first, followed by derived fields, respecting default values) [cite: 48]. Additionally, fields wrapped in `dataclasses.field(init=False)` must be correctly excluded from the constructor signature [cite: 47, 48]. With `NamedTuple`, accessing an attribute acts as a descriptor property, and a code graph must model this as an edge to the underlying tuple index [cite: 49, 50].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Python 3.7+ for native `@dataclass`, standard `typing` module for `NamedTuple`.
* **Classification:** 
  Normative language-defined semantics (standard library).
* **Direct citations to the primary sources supporting the item:** 
  [cite: 47, 49], [cite: 48, 50].
* **Confidence:**

### 2.5. Type Hinting, Static Analysis, and Ecosystem Conventions

#### 2.5.1. Conditional Imports (`TYPE_CHECKING`)

* **Report-local stable identifier:** `PY-TYP-001`
* **Feature or behavior name:** Conditional Typing Imports (`TYPE_CHECKING`)
* **Description of the materially distinct behavior:** 
  The introduction of static typing to Python (PEP 484) created a paradox: adding type annotations often requires importing classes from other modules, which drastically increases the likelihood of circular imports (where Module A imports Module B, which simultaneously imports Module A) [cite: 28, 52]. To resolve this, the typing ecosystem introduced the `typing.TYPE_CHECKING` constant. At runtime, the Python interpreter evaluates this constant to `False`, ignoring the import block entirely and preventing the circular dependency [cite: 53, 54]. However, static type checkers (like mypy, pyright) and static code-graph generators are programmed to evaluate `TYPE_CHECKING` as `True`, allowing them to read the imports and validate the annotations [cite: 52, 54]. This creates a bifurcated codebase where the static reality differs fundamentally from the runtime reality. A code-graph generator must deliberately evaluate the `if TYPE_CHECKING:` branches to build a complete dependency graph [cite: 53, 55]. 
* **Observable project content that would demonstrate it:** 
  Two modules, `module_a.py` and `module_b.py`. `module_a` defines `ClassA` and imports `ClassB` inside an `if TYPE_CHECKING:` block to use it as a return type annotation, safely enclosed in string quotes (or leveraging PEP 563). `module_b` imports `ClassA` at the top level. The code graph must extract the semantic edge from `module_a` to `ClassB` via the type annotation, proving it correctly processes the conditional typing block without throwing a circular import error.
* **Important variants, interactions, counterexamples, and failure cases:** 
  Because the imports inside the `TYPE_CHECKING` block are not available at runtime, the actual type annotations using those imported classes must be declared as string literals (forward references) to prevent the interpreter from raising a `NameError` [cite: 53, 55]. A code-graph generator failing to parse these stringified forward references will miss the type edges entirely. Furthermore, using `if typing.TYPE_CHECKING:` versus `from typing import TYPE_CHECKING; if TYPE_CHECKING:` requires the static analyzer to trace the origin of the variable correctly [cite: 52, 53].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Core feature of the `typing` module, prevalent across modern Python (3.5+).
* **Classification:** 
  Normative static analysis convention.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 53, 56], [cite: 52, 54].
* **Confidence:** 
  High.

#### 2.5.2. Postponed Evaluation of Annotations (PEP 563)

* **Report-local stable identifier:** `PY-TYP-002`
* **Feature or behavior name:** Postponed Evaluation of Annotations (PEP 563)
* **Description of the materially distinct behavior:** 
  Historically, Python eagerly evaluated type annotations at the exact moment a function or class was defined. This caused immense friction due to the performance overhead of executing complex type expressions, and the frequent `NameError` exceptions raised when referencing types that had not yet been fully parsed (forward references) [cite: 57, 58]. PEP 563 addressed this by allowing developers to opt into postponed evaluation using the compiler directive `from __future__ import annotations`. When activated, the Python compiler completely ceases runtime evaluation of annotations within that module. Instead, it captures the raw AST of the annotation, converts it directly to a string literal, and stores it in the `__annotations__` dictionary [cite: 59, 60]. For a code-graph generator, encountering this `__future__` import fundamentally changes how the AST is processed. The graph generator must not treat annotations as standard evaluated expressions; it must understand that the strings contained in `__annotations__` are valid, delayed Python expressions and invoke a secondary parsing pass to map the string contents back to semantic entities [cite: 59, 61].
* **Observable project content that would demonstrate it:** 
  A module starting with `from __future__ import annotations`, followed by a class `Tree` with a method `def add_child(self, node: Tree): pass`. Because the class `Tree` is not fully initialized when the method is parsed, eager evaluation would normally crash. The code graph must trace the `node` parameter's type back to the `Tree` class itself, unwrapping the stringified AST injected by the compiler.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The evolution of this feature is highly controversial. PEP 563 was slated to become the default behavior in Python 3.10 but was rolled back due to massive breakage in libraries (like Pydantic and FastAPI) that rely on evaluating annotations at runtime using `typing.get_type_hints()` [cite: 58, 61]. The scoping rules of PEP 563 string evaluation are fragile: local variables used in annotations often fail to resolve properly at runtime [cite: 59, 61]. A subsequent proposal, PEP 649 (lazy evaluation via descriptors), has been approved for future Python versions (3.14+), creating a fragmented ecosystem where graph generators must support multiple concurrent evaluation semantics [cite: 57, 60].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Python 3.7+ via `__future__`.
* **Classification:** 
  Normative language compiler directive.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 59, 60], [cite: 57, 61].
* **Confidence:** 
  High.

#### 2.5.3. Type Parameter Syntax and Generics (PEP 695)

* **Report-local stable identifier:** `PY-TYP-003`
* **Feature or behavior name:** Type Parameter Syntax and Generics (PEP 695)
* **Description of the materially distinct behavior:** 
  Before Python 3.12, defining generic classes and functions required cumbersome, disjointed syntax involving the manual instantiation of `typing.TypeVar` at the global module scope (e.g., `T = TypeVar('T')`) [cite: 62, 63]. This syntax felt "bolted on" and heavily confused static analysis tools regarding scoping, as a globally defined `TypeVar` could be reused in entirely different, semantically unrelated generic contexts [cite: 63]. PEP 695 revolutionized this by introducing native syntax for type parameters directly in the declaration of classes, functions, and type aliases (e.g., `class Queue[T]:` and `def first[T](elements: list[T]) -> T:`) [cite: 62, 63]. For a code-graph generator, this represents the addition of entirely new AST nodes and scoping paradigms. The variables bound inside the square brackets `[T]` are intrinsically scoped *only* to the entity they decorate. The graph must generate specific type-variable nodes and draw tightly scoped edges connecting the generic parameters in the signature to their usages within the function or class body, preventing leakage into the global module scope [cite: 63, 64].
* **Observable project content that would demonstrate it:** 
  A generic type alias declared using the new `type` statement (e.g., `type ListOrSet[T: (int, str)] = list[T] | set[T]`), and a generic function `def process[T](data: ListOrSet[T]) -> T:`. The code graph must correctly construct the `ListOrSet` alias, evaluate the constraint that `T` must be `int` or `str`, and map the flow of the generic type `T` from the function signature to the return type.
* **Important variants, interactions, counterexamples, and failure cases:** 
  The interaction between PEP 695 syntax and older typing constructs is a major failure point. Older graph generators leveraging pre-3.12 parsers will completely fail to parse the `type` keyword or the `[T]` syntax, yielding syntax errors. Furthermore, PEP 695 type parameters introduce complex covariance and contravariance inference natively, bypassing the explicit `covariant=True` flags previously required in `TypeVar` [cite: 62, 63].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Strictly requires Python 3.12 or higher.
* **Classification:** 
  Normative language-defined semantics.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 62, 63], [cite: 64, 65].
* **Confidence:** 
  High.

#### 2.5.4. Ecosystem Type Hinting Distribution (`py.typed` / PEP 561)

* **Report-local stable identifier:** `PY-TYP-004`
* **Feature or behavior name:** Ecosystem Type Hinting Distribution (`py.typed`)
* **Description of the materially distinct behavior:** 
  When a package is distributed and installed via PyPI, static analysis tools (like mypy or Pyright) must decide whether to trust the type annotations contained within that package. Because many older Python packages contain partial or historically inaccurate type hints, PEP 561 established a strict ecosystem convention: a static type checker must completely ignore the inline type annotations of a third-party package unless that package explicitly contains an empty marker file named `py.typed` at its root [cite: 66, 67]. If the `py.typed` file is absent, type checkers will treat all imports from that library as `Any` [cite: 67]. Alternatively, types can be distributed in completely separate packages called "stub files" (using the `.pyi` extension), either alongside the source or via repositories like `typeshed` [cite: 66, 68]. For a code-graph generator, this necessitates dual-mode file parsing. The generator must search for `.pyi` stub files, which take precedence over `.py` files for type information. Furthermore, to accurately simulate how a modern language server views dependencies, the graph should theoretically evaluate the presence of `py.typed` to dictate the strictness and visibility of typing edges [cite: 69, 70].
* **Observable project content that would demonstrate it:** 
  A distributed package fixture containing heavily annotated source code, but explicitly omitting the `py.typed` file. An external module imports a function from this package. Depending on the configuration constraints of the code-graph generator, the resulting type edge could either resolve to the inferred source types or strictly degrade to `Any`. Another fixture should demonstrate a `.pyi` stub file residing next to a `.py` file, where the code graph accurately extracts the function signatures exclusively from the `.pyi` stub file, ignoring the implementation [cite: 66, 70].
* **Important variants, interactions, counterexamples, and failure cases:** 
  A common edge case involves partial stub packages (e.g., `pandas-stubs`) installed independently of the main library. Graph generators must overlay the abstract syntax tree of the stub package onto the implementation package [cite: 66, 67]. Additionally, many developers falsely assume that merely adding type hints is sufficient; failing to add the `py.typed` marker to `pyproject.toml` package data causes widespread failure in downstream static analysis tools [cite: 67, 70].
* **Language, toolchain, implementation, platform, package-manager, version, and configuration constraints:** 
  Python 3.5+, mandated by PEP 561, heavily utilized by static checkers (`mypy`, `pyright`).
* **Classification:** 
  Ecosystem convention and static analysis standard.
* **Direct citations to the primary sources supporting the item:** 
  [cite: 66, 67], [cite: 68, 70].
* **Confidence:** 
  High.

## 3. Completeness Review

### Recommended Baseline Version and Implementation Assumptions
To construct an idiomatic, comprehensive reference project that effectively evaluates modern code-graph generators, the recommended baseline version is **Python 3.12**. This version encompasses the most radical syntactic and structural changes of the modern era, specifically PEP 634 (Structural Pattern Matching, introduced in 3.10) [cite: 43, 44], PEP 654 (Exception Groups, introduced in 3.11) [cite: 71, 72], and PEP 695 (Type Parameter Syntax, introduced in 3.12) [cite: 62, 63]. Furthermore, Python 3.12 represents a stabilization point for packaging standards like PEP 621 (`pyproject.toml`) [cite: 17, 18] and the complete deprecation of legacy modules like `distutils` [cite: 64, 73]. The implementation assumption should be the standard CPython runtime, as many ecosystem conventions implicitly rely on CPython's specific garbage collection and method resolution timings.

### Material Changes Across Recent Supported Versions
The Python language has witnessed profound material changes that heavily impact graph topology. 
* **Python 3.10** introduced `match`/`case`, fundamentally altering variable scoping and destructuring [cite: 43, 45]. 
* **Python 3.11** introduced `ExceptionGroup` and the `except*` syntax (PEP 654), which allows a program to handle multiple unrelated exceptions simultaneously, requiring graph generators to model 1-to-many exception handling control flows [cite: 71, 72]. It also introduced `Variadic Generics` (PEP 646), enabling parameterization of numerical arrays (e.g., NumPy shapes) [cite: 71].
* **Python 3.12** formalized `f-strings` syntactically (PEP 701), allowing the reuse of quotes and complex nesting within string interpolations, breaking many older regex-based AST parsers [cite: 64, 72]. It also introduced `@override` decorators (PEP 698) for explicit method overriding validation [cite: 62, 64].

### Behaviors That Cannot Coexist in One Configuration
A singular reference project cannot simultaneously exercise a "Flat Layout" and a "Source (`src/`) Layout" natively for the same root module, as their fundamental `sys.path` implications are mutually exclusive [cite: 6, 7]. A robust test fixture must logically partition these architectures into separate, isolated sub-workspaces to evaluate the graph generator's ability to transition its module resolution strategy based on repository context. Similarly, the evaluation of type hints cannot simultaneously demonstrate both the eager evaluation failure modes and the PEP 563 postponed evaluation success modes in the same file; they require disparate test modules with and without the `from __future__ import annotations` directive [cite: 57, 59].

### Features Commonly Omitted from Language Demonstrations
Language demonstrations and elementary test fixtures almost universally omit runtime dynamic imports (`importlib`) and the complexities of the descriptor protocol. Demonstrations usually focus on static class inheritance and simple function calls. However, as documented, frameworks like Django, SQLAlchemy, and modern plugin architectures rely entirely on metaclasses, descriptors, and dynamic string-based module resolution [cite: 26, 37]. These features are chronically under-tested in code-graph generators, resulting in severe accuracy drops when moving from toy projects to production enterprise codebases.

### Areas Where Authoritative Sources Disagree or Remain Unclear
A massive fissure in authoritative guidance exists around the future of type annotation evaluation. The static typing community strongly pushed for PEP 563 (stringified postponed evaluation) as the permanent solution to parsing overhead and forward references [cite: 59, 61]. However, runtime validation communities (e.g., maintainers of Pydantic and FastAPI) vehemently opposed PEP 563 becoming the default, citing catastrophic breakage of runtime type reflection [cite: 57, 61]. The Python Steering Council intervened, rolling back the default mandate and eventually approving PEP 649 (lazy evaluation via descriptors) for Python 3.14 [cite: 57, 60]. Currently, there is deep ambiguity regarding exactly how a static code graph should resolve annotations across versions 3.10 to 3.13, forcing tools to implement complex, heuristic-driven fallback mechanisms.

### Likely Categories, Features, and Interactions Still Missing After the Main Investigation
While this checklist exhaustively covers the semantic entities and module resolution algorithms critical to a code graph, it intentionally circumvents several edge domains. Missing from this investigation is the nuanced behavior of C-extensions and foreign function interfaces (FFI, `ctypes`, `cffi`), which generate binary modules invisible to standard AST parsers. Furthermore, the report does not delve into the complex graph implications of asynchronous control flows (`asyncio`, `await`, coroutines) and context managers (`__enter__`, `__exit__`), which synthesize hidden control-flow edges. Finally, the nuances of specialized Python implementations (PyPy, Jython, MicroPython) and their idiosyncratic runtime behaviors remain outside the scope of this baseline CPython investigation. 

**Unresolved Research Gaps**
1. Establishing a deterministic algorithm for statically inferring the targets of `importlib.import_module` without executing arbitrary code.
2. Formulating a standardized graph schema representation for the C3 Method Resolution Order in the presence of dynamic metaclasses.
3. Quantifying the precise impact of `py.typed` marker omission on the accuracy scores of enterprise-grade static analysis tools across massive monorepos.
