# Dart semantic coverage candidate checklist

## Scope and baseline assumptions

This report identifies materially distinct Dart language, library, package, build, and platform behaviors that a broad self-contained reference project could demonstrate. It does not prescribe source layout, graph structure, scoring, or analysis technology.

- **Baseline:** sound-null-safe Dart 3.x, run with an explicitly recorded stable Dart SDK version. The package SDK constraint should make its language version unambiguous.
- **Implementations:** Dart analyzer/common front end plus Dart VM are the semantic baseline. JavaScript and WebAssembly compilation, native compilation, and platform interoperation are separate configurations where noted.
- **Package assumptions:** modern `pubspec.yaml`, package URIs for public package libraries, and current `dart analyze`, `dart test`, `dart run`, and compilation commands.
- **Reproducibility:** retain the resolved dependency lockfile for applications and executable projects. Record the operating system, architecture, SDK channel, compiler target, experiment flags, defines, and analyzer options used for each observation.
- **Version caution:** “Dart 3.x” spans material language additions. A fixture should pin a concrete SDK rather than assume all Dart 3 releases accept the same syntax.

Each row supplies a stable report-local identifier, the behavior to cover, observable evidence, important variants or failures, constraints and authority, confidence, and a likely primary verification source. Source names are intentionally general where an exact section is not confidently known.

## Recent-version changes requiring explicit verification

The following families materially changed within Dart 3.x or immediately before it. Exact introduction and refinement releases should be checked against the pinned SDK rather than inferred from this report.

- **Dart 3 baseline:** records, patterns, switch expressions, exhaustive analysis, and class modifiers became stable language features. Dart 3 also completed removal of unsound pre-null-safety execution in current toolchains.
- **Dart 3.3 era:** extension types became stable. Their representation, interface, erasure, and interop rules are materially different from extension methods and wrapper classes.
- **Later Dart 3 releases:** type promotion expanded, notably promotion of eligible private final fields and related “why not promoted” analysis. Wildcard/underscore binding rules also evolved.
- **Recent collection syntax:** null-aware collection elements and related null-aware syntax were added after the initial Dart 3 release.
- **Recent contextual syntax:** dot shorthand or similar context-dependent static-member access is recent and its exact supported forms must be verified against the selected SDK.
- **Pub evolution:** workspace support, separate resolution override files, native assets/hooks, and Wasm workflows require relatively recent SDKs and may impose a higher minimum SDK constraint.
- **Interop migration:** modern static JavaScript interop using `dart:js_interop` and extension types supersedes many legacy `dart:js`/`package:js` patterns, but compatibility and backend support remain version-sensitive.
- **Macros/augmentation:** experimental designs changed materially and stable availability must not be assumed. Treat accepted or rejected syntax as an explicitly versioned observation.
- **Formatting/analyzer behavior:** formatter style, lint sets, diagnostic codes, inference, and flow analysis can change even when runtime behavior does not.

## Implementation-defined, target-dependent, or unspecified areas

- Exact evaluation and initialization ordering should be asserted only where the language specifies it. Optimization, allocation, inlining, and object layout are backend details.
- `runtimeType` textual form, minified names, stack-trace text, generated symbol names, error messages, and source-map presentation are not portable identities.
- Integer range/representation, JavaScript number behavior, identity of some primitive values, floating-point edge behavior, and typed-data backing can differ by compiler target.
- Event-loop scheduling is constrained by APIs but host integration, timer granularity, process lifetime, and some ordering details vary by runtime.
- Tree shaking, deferred chunk boundaries, reflection retention, pragma effects, and optimization decisions are implementation-defined.
- Isolate availability, sendability details, spawn behavior, and shared/transferable memory facilities vary by platform and SDK.
- FFI Application Binary Interface (ABI), symbol lookup, structure layout within declared rules, calling convention, dynamic-library naming, and native asset linking are platform-specific.
- File paths, case sensitivity, environment, encodings, signals, and process behavior are host-specific.
- Analyzer lints, severities, plugin diagnostics, generated-file treatment, and doc-link resolution exceed the core language contract.
- Package solving is deterministic for fixed inputs/tool version, but selected versions can change with repository state, yanks, prereleases, SDK constraints, and Pub version.

## Known uncertainty and incomplete areas

- Exact stable SDK release numbers for null-aware collection elements, dot shorthand, wildcard refinements, workspace features, native hooks/assets, and current Wasm support need primary-source verification.
- The current status of macros, augmentation declarations, and any replacement metaprogramming design is deliberately marked low confidence.
- Exact variance support and syntax beyond long-standing Dart generic subtyping needs verification against the selected language version.
- Current web library guidance may have shifted from `dart:html` toward newer web packages and interop APIs.
- Fine details of canonical identity for numbers, records containing special numeric values, generic constants, and compiler targets deserve executable confirmation plus specification review.
- Isolate message sendability differs between same-code and cross-code isolates and may have evolved.
- Native assets/hooks and FFI callback/thread rules are evolving and need OS/architecture-specific verification.
- Pub workspace edge cases, override-file names/precedence, and package publication interaction need current Pub documentation.
- Dartdoc macro/template behavior, analyzer plugin configuration, and generated-source ignore conventions are tool-version-sensitive ecosystem areas.
- Flutter-specific semantics are not enumerated except where Flutter SDK constraints affect Pub resolution. Flutter widget behavior is framework behavior rather than Dart language behavior.
