# Canonical Dart language-feature checklist

## Scope and use

This checklist reconciles the Codex (`C`), Fable (`F`), and Google Deep Research (`G`) reports. It defines observable Dart behavior only. It does not choose a project theme, source layout, or downstream use.

Use a pinned stable Dart Software Development Kit (SDK), record the package and per-library language versions, and record every compiler target, command-line define, experiment flag, analyzer option, operating system, and architecture used. The stable common baseline in the reports is sound-null-safe Dart 3.x. Dart 3.8 is the newest explicitly researched stable baseline, but later or experimental items remain conditional until verified against the pinned SDK.

Status meanings:

- **Required**: every broad Dart fixture must demonstrate the behavior, including an isolated failure case where specified.
- **Conditional**: required only in the stated version, target, platform, package, or ecosystem configuration; mutually exclusive configurations must remain separate.
- **Unresolved research gap**: plausible or disputed; do not treat it as a required stable feature until primary-source verification closes the gap.

Classification uses the requested four values. Toolchain behavior is classified **implementation-defined**. Package and framework practices are **ecosystem convention** even when an official tool enforces them.

## 13. Completeness audit

### Input-report items omitted during synthesis

No materially distinct proposed behavior was silently dropped. Report-local duplicates were merged into the canonical items above. The following were deliberately not promoted to checklist items:

- Pure lexical trivia, broad standard-library API enumeration, and generic deployment/security concerns: the reports themselves classify these as non-semantic or out of scope.
- Framework-specific Flutter widget, asset, plugin, and hot-reload behavior: all reports separate framework behavior from Dart language behavior. Flutter SDK constraints remain represented under manifest and platform items.
- Package publishing protocol, hosted-server internals, signing, trust, and deployment topology: operational concerns without a distinct Dart source semantic in the reports.
- Obfuscation, coverage, source maps, and hot reload as standalone families: retained only where they alter observability, compilation, or platform expectations.
- Stable macros as a positive feature: primary-source-backed cancellation makes absence the required constraint. Augmentations remain DART-GAP-001.

### Categories represented by only one source

- **F only:** standalone scripts (DART-GAP-006), `dart fix`/data-driven fixes (DART-CAN-DIAG-007), `@docImport` detail, pubspec `platforms:` metadata, and several synthetic-entity formulations. The verified mechanisms are conditional; unsupported details remain gaps.
- **C only:** dedicated string, symbol, typed-data, filesystem/process, native-assets, pragma, and low-level value coverage. These are retained because they are plausible and tied to named official APIs, but platform-specific items are conditional.
- **G only:** no stable canonical behavior is unique after reconciliation. Its strongest unique claim is stable/emerging augmentation adoption, which conflicts with C/F uncertainty and remains DART-GAP-001.

### Weak or missing primary evidence

- Exact version and syntax for augmentations, dot shorthand, workspace introduction, native assets, generic annotations, accessor-pair relaxation, and alias static access.
- Current tool behavior for relative-versus-package URI identity and standalone script package resolution.
- Precise pattern getter evaluation guarantees, deferred-load-unit constant identity, isolate sendability partitions, dart2wasm restrictions, and current analyzer/CFE disagreements.
- Complete backend pragma catalog, full `dart_test.yaml` schema, builder edge cases, and analyzer-plugin/custom-lint behavior.

### Likely blind spots for another research pass

- Flutter-specific language-adjacent project structure, plugin federation, asset bundling, platform channels, and generated registrants.
- Custom analyzer plugins/custom lints, kernel (`.dill`) and snapshot formats, custom embedders, source maps/obfuscation, and hot reload/restart semantics.
- Publication-time behavior, hosted package protocol, yanks/content hashes over time, native cross-compilation matrices, and Java/Objective-C interoperability generators.
- Internationalization, protocol/schema generation, dependency-injection registries, and large code-generation pipelines where semantic edges originate in non-Dart assets.
